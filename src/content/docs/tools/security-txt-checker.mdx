The tool page is [tamperbox.dev/security-txt-checker](https://tamperbox.dev/security-txt-checker). It opens on a sample shop's file, a fixture on the reserved `.example` zone, says whether the file is valid, and writes the corrected one. This page is the long version: how the file is fetched, every rule from [RFC 9116](https://www.rfc-editor.org/rfc/rfc9116) the tool applies, what each finding means, and how to fix and publish the file.

<div class="tb-callout"><strong>Where processing happens:</strong> a host name is sent to the Tamperbox server, which requests one file over HTTPS and returns it. A pasted file is read in your browser and never uploaded. The same parser reads both, so a pasted file and a fetched one get the same report. Nothing is stored.</div>

## What the tool answers

1. **Does the host publish a security.txt where researchers look for it?** That is `https://host/.well-known/security.txt`, answered with HTTP 200 and `text/plain`.
2. **Is the file valid under RFC 9116?** At least one Contact, exactly one Expires that has not passed, well-formed lines and URIs, and a Canonical that names the address it came from.
3. **What does a researcher learn from it?** Where to report, in which order, which key to encrypt with, which policy to read first and in which languages.
4. **What should be published instead?** A corrected file, or a drafted one when the host has none.

## Inputs

### A host name

`example.com` or `www.example.com`. A full address is reduced to its host: `https://example.com/about` checks `example.com`, and the field shows the host with a note saying so. The check runs when you stop typing, or on Enter. IP addresses, user names and passwords, and ports other than 80 and 443 are refused before anything is sent. Each host is checked separately: RFC 9116 [section 3.1](https://www.rfc-editor.org/rfc/rfc9116#section-3.1) says a file "MUST only apply to the domain or IP address in the URI used to retrieve it", so `example.com` and `www.example.com` need their own file, or a redirect.

### A pasted file

Paste the text of a security.txt. The field is read as a file when it has a line break, or when it starts with `#`, a PGP header or a `Name: value` line (an `https://` address is not a field). A pasted file is given a final line break if the clipboard dropped it, because that is not the file's fault. A pasted file has no fetch address, so the status, media type and Canonical checks do not apply to it. The field takes up to 70,000 characters; a dropped or opened `.txt` file up to 64 KB.

## Reading the result

### Verdict and chips

"Valid security.txt." with the number of contacts and the days to expiry, "Not valid:" with the worst problem, or "No security.txt." with the status the address answered. The line under it gives the address the file came from, the redirects followed and the date of the check. Chips count problems and things to check, contacts, and the expiry; each jumps to its section.

### Findings

Every problem, errors first. A finding tied to a line has a Show line button that marks the line in the file listing and scrolls the page to it.

### History and Take it further

History lists what Break it and Heal it replaced, with Revert and Reset input. Take it further hands three values from the file to other tools: the domain of the first `mailto:` Contact to the [MX and email domain checker](https://tamperbox.dev/email-domain), so you can see whether that address can receive mail; the Canonical address, when it differs from the one fetched, to the [redirect checker](https://tamperbox.dev/redirect-checker), which shows why they differ; and Expires as a Unix timestamp to the [timestamp converter](https://tamperbox.dev/unix-timestamp).

### What a researcher sees

The file read in the order a researcher uses it: Report to (each Contact with its kind, the first marked), Encrypt with, Read first, Thanks, Languages with their names, Canonical, Hiring, Advisories and any other fields. Missing fields say what the researcher loses.

### Expiry

A time axis with the check, the one-year mark and the file's Expires date, coloured by status, and one sentence on what it means.

### The file as served

The file line by line with numbers. Problem lines are marked with their finding, and comment lines are dimmed. The listing is shown in full.

### Corrected security.txt, or Write a security.txt

When a repair applies, the corrected file to copy or download. When the host has no file, a form writes one from a Contact you supply, with Expires filled in 364 days ahead and Canonical set to the address the file belongs at.

## Method

Errors (FAIL) make the file invalid under RFC 9116; warnings (CHECK) flag something to fix that does not.

### Fetching

The server requests only `https://host/.well-known/security.txt`, the location [section 3](https://www.rfc-editor.org/rfc/rfc9116#section-3) requires: "organizations MUST place the "security.txt" file under the "/.well-known/" path" (the well-known URI scheme is [RFC 8615](https://www.rfc-editor.org/rfc/rfc8615#section-3)). The same section requires that "the file access MUST use the "https" scheme", so up to five redirects are followed and each must stay on `https://`; a redirect to `http://`, a loop or a sixth redirect stops the check with an error. At most 64 KiB are read.

| Response | Finding |
| --- | --- |
| Status other than 200 | Not served (FAIL), and the draft form instead of a report |
| A web page (`text/html`) with status 200 | Wrong media type (FAIL), and the draft form |
| Any other type than `text/plain`, or a charset other than `utf-8` | Wrong media type (FAIL) |
| Not valid UTF-8 | Not UTF-8 (FAIL) |
| More than 64 KiB | Larger than 64 KiB (FAIL) |

Section 3: "It MUST have a Content-Type of "text/plain" with the default charset parameter set to "utf-8"". [Section 4](https://www.rfc-editor.org/rfc/rfc9116#section-4) adds that the file "MUST be encoded using UTF-8".

### Lines

Blank lines and lines starting with `#` are skipped ([section 2.1](https://www.rfc-editor.org/rfc/rfc9116#section-2.1)). Every other line must match the grammar in [section 4](https://www.rfc-editor.org/rfc/rfc9116#section-4), `field-name fs SP value`: a name, a colon, a space and a non-empty value, with no control characters. Anything else is "Not a field line" (FAIL) on its line number. Field names are case-insensitive. Every line must end with a line break ([section 2.2](https://www.rfc-editor.org/rfc/rfc9116#section-2.2): "Every line MUST end with either a carriage return and line feed characters (CRLF / %x0D %x0A) or just a line feed character"), so a fetched file whose last line has none gets "Last line has no line break" (FAIL). Fields RFC 9116 does not define are listed, not flagged, as [section 2.4](https://www.rfc-editor.org/rfc/rfc9116#section-2.4) asks readers to ignore fields they do not support.

### Required fields

| Rule | Source | Finding |
| --- | --- | --- |
| At least one Contact | [2.5.3](https://www.rfc-editor.org/rfc/rfc9116#section-2.5.3): "This field MUST always be present" | No way to report (FAIL) |
| Exactly one Expires | [2.5.5](https://www.rfc-editor.org/rfc/rfc9116#section-2.5.5): "This field MUST always be present and MUST NOT appear more than once" | No Expires date, or Expires appears more than once (FAIL) |
| At most one Preferred-Languages | [2.5.8](https://www.rfc-editor.org/rfc/rfc9116#section-2.5.8): "This field MUST NOT appear more than once" | Preferred-Languages repeated (FAIL) |
| Valid language tags | 2.5.8, tags as in RFC 5646 | Not a language tag (FAIL) |

### Expires

The value must be an [RFC 3339 date-time](https://www.rfc-editor.org/rfc/rfc3339#section-5.6): date, `T`, hours, minutes, seconds, optional fractional seconds, then `Z` or an offset. `t` and `z` are accepted in lower case, as RFC 3339 allows. The month, day, hour, minute and offset are checked against the calendar, so `2027-02-30T00:00:00Z` and a bare `2027-03-01` both fail as "Expires is not a date" (FAIL).

- At or before the moment of the check: "The file has expired" (FAIL). Section 2.5.5 says the data is then "considered stale and should not be used".
- More than 366 days ahead: "Expires more than a year ahead" (CHECK). Section 2.5.5: "It is RECOMMENDED that the value of this field be less than a year into the future to avoid staleness."

A fetched file is judged at the moment of the check; a pasted file at the moment you paste it.

### URIs

Contact, Canonical, Encryption, Policy, Hiring and Acknowledgments must hold an absolute URI: a scheme, a colon, no spaces or non-ASCII characters, and only valid `%` escapes. A bare `security@example.com` is "Not an absolute URI" (FAIL); write `mailto:security@example.com`. A web URI must use HTTPS: each field's section says "If this field indicates a web URI, then it MUST begin with "https://"", so `http://` is "A web address uses http://" (FAIL). CSAF lines are listed but not validated.

### Canonical

When the file has Canonical lines, one must equal the URL the file was finally fetched from, character for character, or the finding is "Canonical points elsewhere" (FAIL). [Section 2.5.2](https://www.rfc-editor.org/rfc/rfc9116#section-2.5.2): "If this field appears within a "security.txt" file and the URI used to retrieve that file is not listed within any canonical fields, then the contents of the file SHOULD NOT be trusted." A file without Canonical lines is not flagged, as the field is optional.

### Signatures

A file starting with `-----BEGIN PGP SIGNED MESSAGE-----` is split from its signature and dash-escaping is removed before the fields are read. A malformed envelope is "Broken signature block" (FAIL). A well-formed one gets "Signed, not verified here" (CHECK): [section 2.3](https://www.rfc-editor.org/rfc/rfc9116#section-2.3) recommends signing, and the tool reads the signature without verifying it.

## Standards and conformance

| Specification | Sections | How the tool applies them | Where it stops |
| --- | --- | --- | --- |
| [RFC 9116](https://www.rfc-editor.org/rfc/rfc9116) security.txt | 2.1 to 2.5.8, 3, 3.1, 4 | One parser on the server and in the browser; errors for every MUST, a warning for the one-year recommendation | Signatures are not verified; the legacy top-level `/security.txt` is not requested; Canonical is compared with the final URL after redirects, so a file reached through a redirect needs the final address listed |
| [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339#section-5.6) | 5.6 | Full date-time with calendar range checks | Leap seconds (`:60`) are refused |
| [RFC 8615](https://www.rfc-editor.org/rfc/rfc8615) | 3 | The well-known path | |
| [RFC 5646](https://www.rfc-editor.org/rfc/rfc5646) language tags | | Well-formedness through the browser's locale canonicalisation | Registry validity of each subtag is not checked |

Section 3 lets a redirect from the top-level path lead to the well-known one; the tool only requests the well-known path, which [section 3](https://www.rfc-editor.org/rfc/rfc9116#section-3) says "MUST be used" when both exist. RFC 9116 is an Informational RFC, not updated or obsoleted by a later RFC at the time of writing; the field registry is kept by [IANA](https://www.iana.org/assignments/security-txt-fields/security-txt-fields.xhtml).

## Finding reference

| Code | Severity | Title | What it means for a researcher | Fix |
| --- | --- | --- | --- | --- |
| http_status | FAIL | Not served | No file to read | Publish the file at the well-known path |
| content_type | FAIL | Wrong media type | Tools see a web page or an unknown type | Serve `text/plain; charset=utf-8` |
| invalid_utf8 | FAIL | Not UTF-8 | Text may be garbled | Save as UTF-8 |
| truncated | FAIL | Larger than 64 KiB | The file cannot be valid | Shorten it |
| invalid_line | FAIL | Not a field line | The line is skipped | "Name: value", or a comment |
| missing_final_newline | FAIL | Last line has no line break | Strict parsers fail | End the last line |
| missing_contact | FAIL | No way to report | Nowhere to send a report | Add a Contact |
| expires_count | FAIL | No Expires date, or Expires appears more than once | The file may be ignored | Exactly one Expires |
| invalid_expires | FAIL | Expires is not a date | The file cannot be trusted | RFC 3339 timestamp |
| expired | FAIL | The file has expired | Contacts may be stale | Re-date within a year |
| distant_expiry | CHECK | Expires more than a year ahead | Reviewed less often than recommended | Bring it within a year |
| insecure_uri | FAIL | A web address uses http:// | A report or key can be read or replaced | Use https:// |
| invalid_uri | FAIL | Not an absolute URI | The value cannot be followed | Write the scheme |
| languages_count | FAIL | Preferred-Languages repeated | Ambiguous | One line, comma-separated |
| invalid_language | FAIL | Not a language tag | Ignored | `en`, `nl`, `pt-BR` |
| canonical_mismatch | FAIL | Canonical points elsewhere | This copy cannot be trusted | List the address it is served from |
| invalid_signature_envelope | FAIL | Broken signature block | The file cannot be read reliably | Sign it again |
| signature_unverified | CHECK | Signed, not verified here | Verify it yourself | |

## Guide

Confirm any fix outside Tamperbox by reading what a researcher's tools read:

```sh
curl -sSI https://example.com/.well-known/security.txt | grep -iE '^(HTTP|content-type|location)'
curl -sS https://example.com/.well-known/security.txt
```

The first line must say 200, the type `text/plain`, and the body must be the file, not a page.

### No file, or a web page at the address

1. Fill in the form under the result: a Contact is required; Expires is filled in for you.
2. Save the file as `/.well-known/security.txt` in the site's static files, or add a route that serves it before the application's catch-all. Single-page apps that answer every path with `index.html` are the usual cause of "Wrong media type".
3. Make sure it is served with `Content-Type: text/plain; charset=utf-8`. A file served as `application/octet-stream` needs a MIME mapping for the path.
4. Check the host again.

### Canonical points elsewhere

List every address the file is served from, or redirect the other hosts to one address and list that one. Heal it's "Point Canonical here" replaces the Canonical lines with the address the file was fetched from. If you sign the file, sign it again after the edit.

### Expired, or more than a year ahead

Set Expires less than a year ahead and put the renewal with your other yearly tasks, such as certificate and domain renewals. Heal it's "Set Expires to …" uses 364 days after the check, at midnight UTC.

### Broken lines and http:// addresses

"No space after a colon" is the commonest broken line (`Contact:mailto:…`). Heal it turns broken lines into comments, so you can rewrite them, and switches `http://` to `https://` in web fields.

### Break it cases

| Case | What it loads | What it shows |
| --- | --- | --- |
| Expired yesterday | Your file with Expires set to yesterday | The file has expired |
| No Contact | Your file without Contact lines | No way to report |
| Expires twice | Your file with a second Expires | Expires appears more than once |
| Contact over http | Your file with one web address switched to http:// | A web address uses http:// |
| No space after a colon | Your file with one field missing its space | Not a field line |
| Served as a web page | A sample host that answers with HTML | Wrong media type and the draft form |
| No security.txt | A sample host that answers 404 | Not served and the draft form |

The first five build on your own file, pasted or fetched, when you entered one. Heal it offers the repairs that apply, one per kind and "Apply all" when there are several, and "Restore input before this break" when none applies. A missing Contact cannot be repaired: no address is invented.

## Worked example

The sample shop `www.harbor-supply.example` is reserved sample data dated 12 October 2026, answered in the browser. Its file has two contacts (an email address, then a report form), an encryption key, a policy, acknowledgments, Preferred-Languages `en, nl`, Canonical `https://harbor-supply.example/.well-known/security.txt` and Expires `2028-01-01T00:00:00Z`. Fetched from `https://www.harbor-supply.example/.well-known/security.txt`, it is not valid: Canonical points elsewhere (FAIL) because it names the bare domain. Expires is 446 days after the check, so it is also more than a year ahead (CHECK). Heal it offers "Point Canonical here", "Set Expires to 2027-10-11" and "Apply all 2 repairs"; the corrected file lists the www address as Canonical. Take it further traces the Canonical address through the redirect checker, where the sample's bare domain redirects to www, which is exactly why the two addresses differ.

## For agents

The Tamperbox MCP server runs the same check as the `security_txt_checker` operation with a public `domain`. Inspect its input schema before calling it. The result carries the file, the status, the media type and a report whose findings use the codes in the [finding reference](#finding-reference). Keep these with any conclusion:

- A valid file is contact information, not permission to test the site.
- The signature, if any, was not verified, and the contacts were not tested.
- Only the well-known path on this exact host was requested.

See [Connect an MCP client](/mcp/connect/) for the calling pattern.

## Limits

- One request path, `/.well-known/security.txt`, over HTTPS, from the Tamperbox server at one moment.
- Up to five HTTPS redirects; 64 KiB.
- OpenPGP signatures are separated and reported, never verified.
- Language tags are checked for form, not against the subtag registry.
- A pasted file is not checked for status, media type or Canonical.
